# Reminders.py — Function-by-function walkthrough

## Summary

A self-contained Discord cog that lets users schedule a message to repeat every week at a given weekday + time, in a chosen channel. When the message fires, the bot appends a Discord relative-time token (`<t:UNIX:R>`) so each viewer sees something like "in 2 hours" rendered in their own timezone. Reminders survive restarts because the in-memory list is mirrored to `src/Reminders.json` after every change.

## Module-level constants

- **`WEEKDAY_NAMES`** — list of weekday strings ordered to match Python's `datetime.weekday()`, where `0 = Monday … 6 = Sunday`. Letting the index be the canonical weekday makes lookups (`WEEKDAY_NAMES[r["weekday"]]`) trivial and keeps storage compact (one int per reminder instead of a string).
- **`WEEKDAY_CHOICES`** — Discord slash commands display dropdowns when you give them a `Choice` list. This precomputes `Choice(name="Monday", value=0) … Choice(name="Sunday", value=6)` so `/reminder add` shows a friendly weekday picker that submits the integer Python wants.
- **`DATA_PATH`** — absolute path to the JSON state file. Built from `__file__` so it resolves correctly regardless of the process's working directory; the `..` collapses `src/cogs/` back up to `src/Reminders.json`.

## Top-level helper functions

### `_load_data()`
Reads the persisted reminder list from `DATA_PATH`. If the file doesn't exist (first run) it returns a fresh empty structure: `{"reminders": [], "next_id": 1}`. The `next_id` counter lives inside the JSON so that ids stay monotonically increasing across restarts — without it, deleted ids could be reused and confuse anyone using `/reminder remove id`.

### `_save_data(data)`
Writes the dict back to `DATA_PATH` in human-readable form (`indent=2`). Called after every state-mutating operation (`add`, `remove`, and inside `tick` whenever a reminder fires) so a crash never silently drops state.

### `_format_reminder(r)`
Builds the one-line textual summary used by `/reminder list`. Composes:
- `` `#1` `` — the reminder id, backticked so Discord renders it monospaced
- `<#123…>` — Discord's channel-mention syntax that turns into a clickable `#channel-name`
- `Tuesday 18:00` — human-readable schedule
- `(lead 120m)` — minutes between firing and the embedded event timestamp
- `'event starts'` — the original message, repr-quoted via `!r` so any embedded backticks or quotes survive intact

## The `Reminders` cog

### `__init__(self, client)`
Stores the bot reference and immediately loads persisted state into `self.data`. From this point on, all reads and writes hit the in-memory dict; the disk file is touched only on save. This avoids re-parsing JSON on every command and keeps the working-set fast.

### `cog_load(self)` *(lifecycle hook)*
discord.py 2.x calls this after the cog has been attached to the bot. It starts the `tick` background task. Starting the loop here (rather than in `__init__`) guarantees the cog is fully wired up before the loop's first iteration tries to send messages.

### `cog_unload(self)` *(lifecycle hook)*
Cancels the `tick` loop when the cog is unloaded or the bot shuts down. Without this, the loop would keep running against a stale cog reference and likely crash on the next tick.

### `reminder_group` *(class attribute, not a function)*
A `discord.app_commands.Group` named `reminder` with `default_permissions=manage_messages`. Everything below it is a subcommand of `/reminder`, which gives the four operations a clean namespace and hides the whole group from users without Manage Messages by default. Server admins can re-bind permissions in *Server Settings → Integrations*.

### `add(self, interaction, channel, weekday, time, lead_minutes, message)` *(slash subcommand)*
Schedules a new reminder. Step by step:

1. **Parse `time`** with `datetime.strptime(..., "%H:%M")`. If the user typed something invalid (e.g. `"25:99"`), reply with an ephemeral error and bail — `strptime` raises `ValueError` on malformed input.
2. **Allocate an id** by reading `self.data["next_id"]` and incrementing it. Each id is unique forever in this state file.
3. **Append a reminder dict** with all the schedule data plus `last_fired: ""`. The empty string is the sentinel for "never fired"; it's compared against today's ISO date later in `tick`.
4. **Persist** via `_save_data` so the new reminder survives a restart.
5. **Confirm** to the user with an ephemeral message containing the new id, formatted weekday, time, and channel mention.

The `lead_minutes` parameter uses `app_commands.Range[int, 0, 10080]` so Discord enforces the 0-to-one-week range client-side; the bot doesn't have to validate it.

### `list_(self, interaction)` *(slash subcommand `/reminder list`)*
Plain listing. If there are no reminders, replies with that. Otherwise joins each reminder's `_format_reminder` output with newlines and sends as one ephemeral message. Method name is `list_` to avoid shadowing the Python builtin; the slash command name is set to `"list"` via the decorator so users still type `/reminder list`.

### `test(self, interaction, id)` *(slash subcommand)*
Fires a reminder right now without affecting its real schedule. Mirrors what `tick` would do for the same reminder, but is triggered manually:

1. **Find** the reminder by id with a `next(...)` generator search; replies with an error if it doesn't exist.
2. **Resolve the channel** via `client.get_channel`. If it returns `None` (channel deleted or the bot can't see it), report that to the user. This is more verbose than the silent skip in `tick` because here the user is actively waiting for feedback.
3. **Recompute the event timestamp from `datetime.now()`** rather than the stored schedule, so a test fire at 4 PM with a 2-hour lead correctly reads "in 2 hours", not "in 2 hours from when this would have fired tonight."
4. **Send** the message. On HTTP failure, surface the error to the user. On success, send an ephemeral confirmation.
5. **Crucially: does not touch `last_fired`** — the next real scheduled fire still happens.

### `remove(self, interaction, id)` *(slash subcommand)*
Drops a reminder. Snapshot the list length, filter out the reminder with the matching id, and compare lengths. If nothing was removed (id wasn't found), tell the user. Otherwise persist and confirm.

### `tick(self)` *(background task, every 30 seconds)*
The scheduler heart of the cog. The decorator `@tasks.loop(seconds=30)` runs this method every 30 seconds in the bot's event loop. Per tick:

1. **Snapshot now**: `now = datetime.now()` once, then derive `today_iso` (e.g. `"2026-05-13"`) for the dedup check.
2. **For each reminder**, three early-exit guards:
   - Skip if today's weekday doesn't match the reminder's `weekday`.
   - Skip if the current `hour:minute` doesn't match. Because the loop runs every 30s and the comparison is at minute granularity, every scheduled minute will match exactly once or twice.
   - Skip if `last_fired` is already today — this is the dedup mechanism that prevents the second tick within the same scheduled minute from re-firing.
3. **Resolve the channel**. If `get_channel` returns `None` (channel deleted, bot kicked, etc.), skip silently.
4. **Compose the message**: `f"{r['message']} <t:{int(event_time.timestamp())}:R>"` where `event_time = now + lead_minutes`. The `<t:UNIX:R>` syntax tells Discord "render as relative time in viewer's local timezone."
5. **Send and mark**. `last_fired` is only updated *after* a successful send, so a transient failure (network blip, rate limit) lets the next tick retry. Any send exception is swallowed to keep the loop alive — one bad reminder shouldn't kill scheduling for the others.
6. **Persist** if any reminder fired. Skipping the write when nothing changed avoids touching the disk every 30 seconds.

There's one subtle race: if the bot restarts during the scheduled minute *between* sending and saving, the reminder could fire twice on the same day. For a small Discord bot this is acceptable and the alternative (saving before sending) would risk silent drops, which feels worse.

### `before_tick(self)` *(loop pre-flight)*
Decorated with `@tick.before_loop`, it runs once before the very first tick and blocks on `self.client.wait_until_ready()`. Without this, the first tick could fire before the gateway has populated the channel cache, in which case `get_channel` would return `None` for everything and silently swallow due reminders.

## Module entry point

### `setup(client)` *(top-level coroutine)*
The entry point discord.py looks for when `bot.load_extension("cogs.Reminders")` runs. It instantiates the cog and registers it with the bot, which is what makes the slash commands discoverable and starts the lifecycle hooks (`cog_load` → `tick.start`).
